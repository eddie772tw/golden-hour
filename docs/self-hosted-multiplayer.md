# 自營多人對戰與可攜帳號設計

本文件保留設計規格與後續階段。已實作的本地帳號、指紋邀請、專服腳本與離線對局流程見[操作說明](../server/dedicated/README.md)。第一版以每服簽署的累計戰績取代逐事件傳檔，唯一事件仍保存在 SQLite；採固定欄序陣列作為簽章編碼。區網自動發現、自訂跨服互信與 TURN 屬後續階段。第一個可交付版本的目標是讓兩台電腦在斷開外網的 Wi-Fi 熱點上，從建立帳號、配對到取得對戰進度都能完成。同一套房間服務也能由社群長期運行。Bilibili、官方帳號、官方房間目錄及官方中繼均不在必要路徑上。

## 現有程式的接點

| 現況 | 改動位置 |
| --- | --- |
| Node 房間以 60 Hz 模擬、30 Hz 發快照，伺服器已裁定裝備、彈藥、傷害、擊殺及逐玩家可見性。 | 保留 [房間模擬](../server/room.mjs) 與 WebRTC 的可靠事件、即時狀態雙通道。 |
| HTTP 的 Host／Origin 檢查、監聽位址、RTC 綁定位址都固定為 loopback。SSE 房間列表只涵蓋目前連上的主機。 | [服務入口](../server/server.mjs) 分開設定監聽介面、對外公告位址、允許的來源與 ICE 連接埠；[房間目錄](../game/client/lobby.js) 增加主機選擇。 |
| 瀏覽器以持有 UUID 格式的秘密字串作為登入憑證，SQLite 以其 SHA-256 摘要辨識舊戰績。進房流程也會呼叫 Toy 授權。 | [對戰入口](../game/client/pvp.js) 改用本地帳號，替換 [舊憑證](../game/client/toy-weapons.js) 以及進房、重連、讀取戰績三處驗證。Toy 保留為選用的舊資料匯入來源。 |

## 玩家怎麼連線

| 玩法 | 房主 | 加入方式 |
| --- | --- | --- |
| 臨時熱點／同一區網 | 一位玩家從啟動器選「開房」，在該電腦啟動 Node 裁判。玩家可先用作業系統建立 Wi-Fi 熱點。 | 其他玩家連上同一網路後，從清單點選房間，或貼上房主的邀請。房主離開會結束當局，已入帳戰績可恢復。 |
| 區網發現與代碼 | 啟動器以 mDNS/DNS-SD 公告及查詢 `_goldenhour._tcp.local.`，找到主機後才向該主機讀取房間清單。 | 同一主機上的短房碼只識別房間。未知主機以完整邀請加入，內容含位址、連接埠、房碼、協定版本與主機公鑰指紋。多台主機出現相同短碼時讓玩家選房主。 |
| 玩家自營專用伺服器 | 管理者在常開的電腦或 VPS 執行同一服務，管理自己的金鑰、信任名單與 SQLite。 | 從已儲存主機、網址或邀請加入。快速配對只在玩家已選定的主機上進行。 |

初版以每位桌面玩家執行本地啟動器為基準。啟動器由固定的 loopback 來源供應隨遊戲發布的前端，並代送到玩家選定主機的信令、目錄與驗證請求；對戰資料通道仍由瀏覽器直接連往房主。帳號資料因此留在玩家自己的來源。代送路徑限制在遊戲協定與已選主機，並驗證本機請求來源。熱點房主可自動產生主機憑證，以完整邀請釘選公鑰；只有區網發現時，首次連線顯示指紋供玩家對照。憑證輪替提供重新配對流程。

行動裝置或純瀏覽器玩家可由可信任的 HTTPS 遊戲前端貼上邀請；此路徑需要目標主機具有瀏覽器信任的 HTTPS 憑證、允許該前端的精確來源，並通過瀏覽器的區網存取權限。帳號解鎖與匯入只在玩家信任的遊戲前端進行。自動發現先由桌面啟動器提供。訪客網路停用多播時可貼邀請；若 AP 啟用用戶端隔離，則需換可彼此到達的網路或使用可達的專服。[DNS-SD](https://www.rfc-editor.org/rfc/rfc6763) · [瀏覽器安全來源](https://www.w3.org/TR/secure-contexts/)

區網採直接 ICE 候選位址，不配置外部服務。跨網優先使用有公網位址的專服，或由房主轉發信令與 RTC 的連接埠。部署腳本要分別檢查兩條路徑；反向代理只轉送 HTTPS 訊號仍可能無法建立對戰通道。雙方網路條件無法直連時，可配置社群自營 TURN 與短效憑證。沒有可達路徑時，畫面應指出失敗環節並提供切換主機的入口。[ICE](https://www.rfc-editor.org/rfc/rfc8445) · [TURN](https://www.rfc-editor.org/rfc/rfc8656)

## 帳號與存檔

| 資料 | v1 格式與用途 |
| --- | --- |
| 帳號身分 | 在本機產生 ECDSA P-256 金鑰。以固定標籤 `GH-account-v1` 的 UTF-8 位元組、零位元組、65 位元組未壓縮 SEC1 公鑰依序計算 SHA-256，取前 16 位元組，設 version 8 與 RFC variant 位元後格式化為 UUID。驗證端重算 UUID，同時比對完整公鑰。兩台未曾互通的伺服器可獨立驗證相同身分。 |
| 個人檔案 | `profile.displayName` 可修改，顯示重名時加上短 UUID。`profile.avatar` 可為空，或包含 MIME、大小、SHA-256 與圖片內容的參照。第一版建議支援本機 PNG／WebP，解碼、縮圖再編碼，限制為 256 × 256、128 KiB。頭像另行按摘要傳送，不放進每幀快照。 |
| 遊戲進度 | 裝備偏好、訓練與外觀進度放在存檔。競技進度另存由對戰主機簽發的紀錄，含帳號 UUID、簽發者、公鑰指紋、唯一事件 ID、武器及已裁定的對人擊殺。解鎖於驗證時按規則重算。 |
| 磁碟與備份 | 版本化的 `.ghsave` 包含私鑰、個人檔案、圖片、偏好與競技紀錄。本機 IndexedDB 及匯出檔皆以 AES-256-GCM 加密；以使用者口令、隨機鹽和 PBKDF2-HMAC-SHA-256 派生金鑰。記錄 KDF 版本與成本，解密前限制參數上限，每次寫入使用新 IV，格式版本等標頭納入附加認證資料。口令只在解鎖時輸入，頁面關閉後再解鎖。 |

雜湊供內容比對，GCM 標籤供本地解密時驗證完整性。帳號簽章證明持有私鑰，戰績簽章證明哪個主機裁定了事件。存檔持有人能改寫客戶端並重新加密自己的資料；配對伺服器仍能獨立查核影響裝備與積分的紀錄。簽署內容使用具版本與用途標籤的固定格式，JSON 採 JCS 正規化。[UUIDv8](https://www.rfc-editor.org/rfc/rfc9562#section-5.8) · [Web Crypto](https://www.w3.org/TR/2017/REC-WebCryptoAPI-20170126/) · [JSON 正規化](https://www.rfc-editor.org/rfc/rfc8785)

## 配對前驗證

1. 玩家先在可信任前端解密存檔，核對格式、必要欄位、圖片摘要、金鑰與 UUID。新玩家可在離線狀態建立零戰績帳號。損壞、版本不相容或口令錯誤時保留原檔，提供重試、還原備份或單人訓練。
2. 選定房主後，專服提供一次性隨機挑戰，以及用戰績金鑰簽署的 TLS 憑證指紋。客戶端用本機啟動器從邀請核對的指紋驗證簽發者，然後送出 UUID、公鑰、名稱、本服最近一份累計憑證及玩家簽章。第一次到訪送出空清單。帳號簽章涵蓋挑戰、簽發者及本次送驗欄位。其他專服的憑證、頭像、口令、私鑰及完整備份都留在本機。
3. 伺服器驗證挑戰時效及單次使用、帳號持鑰、結構與紀錄簽章，以資料庫去除重複事件，再發短效、一次性、綁定帳號及目標主機的入場票。建立／加入／快速配對都先驗票才分配席位。斷線重連需同一帳號再次證明持鑰，並驗既有房間與席位的恢復憑證。戰績查詢改用同一驗證流程建立的短效會話。
4. 偽造、錯綁帳號、無效簽章或被竄改的送驗資料會被擋在配對外。來源簽章有效、但目標服未採認的紀錄保留在玩家存檔，可正常配對；該服只依採認的紀錄開放武器。UI 在加入前顯示可用裝備與原因。現行 KR-7 對真人 10 殺開 VESPER、VESPER 對真人 10 殺開 M12 的門檻照用。

預設每台服信任自己，只統計本服排行榜。社群可手動互信簽發公鑰，採計彼此進度。自營房主能替自己簽發虛假戰績；完全離線的其他主機無從判定那場比賽是否真實，因此陌生房主的簽章不會自動產生跨服戰力。每台服保留最小驗證與稽核資料、戰績及已簽發事件，不必保存玩家完整存檔。結算先持久化，再交付簽章紀錄；斷線後相同帳號可補領，重領沿用同一事件 ID。

現有可靠通道的單筆訊息上限為 16 KiB。准入資料及首次同步的歷史紀錄改走有大小、頁數與時效限制的 HTTPS 請求；之後依主機已驗收的紀錄摘要做增量同步。短效票放入 RTC hello。完整邀請可以轉貼，裡面只放公開定位資料，不放入場票、帳號憑證或 TURN 長期密碼。

## 搬移、共用及舊檔

- 匯出後可用 USB、區網傳檔或玩家自選的同步資料夾搬到另一台設備。在新設備先完整解密、預覽 UUID 與名稱再寫入；匯入失敗保留既有帳號。另一台匯入相同備份後共用同一身分。備份與口令同時交給他人，也把該身分的控制權交給對方。
- 同 UUID、同公鑰的多份存檔依簽發者與事件 ID 合併戰績。同鍵不同內容視為衝突，不入帳；偏好、名稱及頭像衝突由玩家選擇。舊備份可還原，已在該服入帳的事件不因還原而扣除或重複增加。同一主機限制同 UUID 同時佔用一個對戰席位。跨越互不連通的主機無法保證全域單一登入。v1 以檔案交換提供共用，無背景同步或官方找回服務。
- 首次升級可以匯入本機名稱、裝備與訓練資料。舊服在本機驗證原 bearer 後，可將自己 SQLite 中的紀錄一次性綁到新 UUID 並簽發；使用交易與唯一約束阻止同一舊身分綁定多次。舊 bearer 只交回原服。只有舊存檔內宣稱的競技擊殺維持未驗證狀態。

## 實作順序與驗收

| 階段 | repo 交付 | 驗收 |
| --- | --- | --- |
| 1．離線帳號及配對准入 | 新增存檔編解碼、匯出／匯入、主機簽章與票證。替換 Toy 配對依賴，沿用本機房間做端到端驗證。 | 封鎖所有外網仍可建立帳號與本機配對。改檔、錯密碼、冒用 UUID、重放挑戰與跳過 hello 驗票均不能取得席位。新身分可開局，舊服遷移可安全重試。 |
| 2．熱點與玩家專服 | 在 `server/dedicated/` 提供 `start.ps1`、`start.sh`、設定範例與部署說明。兩個腳本共用既有 Node 入口；啟動檢查相依套件、宣告位址、TLS、RTC 埠、持久金鑰與資料目錄，輸出邀請及診斷資訊。啟動器先支援貼邀請與指定主機＋短碼。 | 預先安裝依賴後，用兩台實體電腦、斷外網熱點完成一局；另一台常開主機可無介面運行、重啟後維持身分與紀錄。錯碼、主機指紋變更、信令通但 RTC 埠不通有不同提示。 |
| 3．發現、跨設備與跨網 | 加入區網主機發現、頭像交換、多設備合併、自營 TURN 設定及五語系提示。 | 測同碼不同主機、多播被擋改貼邀請、兩台設備共用 UUID、同服二次登入、舊備份重播、未知簽發者、跨 NAT 直連與中繼。回歸逐玩家隱藏、10 殺解鎖、補領不灌榜。 |

優先交付可在同一熱點實際完賽的版本。自動發現、跨網中繼與社群互信可獨立交付；各玩法共用一套存檔格式、准入驗證與對戰裁判。
